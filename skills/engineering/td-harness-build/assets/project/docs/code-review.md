# 代码审阅（Code Review）规范

> **用途**：独立语义审阅（Semantic Review）：判断设计、实现与需求是否一致，代码是否便于理解和修改。执行角色与交接见 [Agent 分工](../agent-roles.md)，检查选择与门槛见 [验证规则](verification.md)。
>
> **记录位置**：本任务的发现、处置与确认写入 **05-review.md**；数值门槛见 [验证规则](verification.md)，工具命令沿用项目规范。

## 1. 审阅准备

开始前按 [Agent 分工 §2](../agent-roles.md#2-派发与返工) 核对独立性、交接及记录归属；检查选择和证据复用按 [验证规则 §1](verification.md#1-检查选择) 执行。

审阅当前 **diff** 及必要上下文，记录实际看过的版本与范围，不假称逐行检查全部代码。按“谁会发现问题、多久发现、损失多大”确定重点。

**先独立理解**：依据需求、契约和实际代码，追踪本次改动的关键行为，定位状态、错误与资源由谁负责；再核对作者交接及验证结论。用简短说明和代码位置记录理解结果，不另写逐行解说。

**有疑点再比较**：指出职责分散、重复路径或阅读跳转等具体负担，必要时比较一个保持契约与行为的替代结构，说明减少了什么理解负担。没有具体问题时不要求另一版实现，也不把“能读懂”直接当作“容易读”。

**规则冲突交主 Agent 处理**：若满足工具门槛的改法反而违反设计规则，记录冲突及影响；不能仅因指标达标放行，也不自行降低门槛。需要例外或越界修改时，按授权规则确认。

交接材料从当前任务读取：

- **需求与范围**：由 **00-overview.md §3** 定位产品需求与 **验收条件（Acceptance Criteria，AC）**，核对 **02-plan.md** 与产品 Overview 中的整体方案和本 Task 启动授权。
- **验证与文档**：读取 **03-implement.md** 的自测证据和 **04-docs.md** 的增量，独立验证结果写入 **05-review.md §3**；区分通过、失败、未验证和不涉及，无文档变化时说明原因。
- **记录归属**：按 AGENTS 的填写规则核对各任务文件的章节与内容职责，允许无适用项时删除记录表；检查必要证据而非空表是否齐全。
- **关键决定与风险**：在 **05-review.md §1** 定位范围，在 **§4** 记录必要处置；详细内容引用原记录。

提交不得夹带无关改动、敏感文件或误提交的生成产物；禁止提交 **.env、_.key、_.pem、credentials.json** 及编译产物。禁止直推保护分支，按项目特性分支与 **PR／MR** 规则提交。

**PR** 说明背景、改动、影响、验证和回滚方式，按需关联 **Issue**。删除已有测试须说明理由；引入新依赖须在 **Commit Message** 说明理由。

## 2. 审阅清单

**需求维度**核对遗漏、错误实现与范围扩张，发现引用对应需求或 AC；**规范维度**核对项目约定，发现引用具体规则。由同一独立 Reviewer 检查，集中报告，实际验证与功能找错仍须完成。

逐项核对本次适用内容。**明确规则和项目强制约束必须满足，工具通过或严重度较低不能豁免。** 启发式提示与设计建议须说明具体位置、问题依据及影响，不凭个人偏好阻断。

### 2.1 业务与安全

- [ ] 符合需求与 **AC**，无范围蔓延；检查空值、长度、并发、重试和幂等等相关边界。
- [ ] 错误处理完整，不静默吞错；忽略错误（如 `_ = err`）有明确理由。
- [ ] **SQL** 参数化；命令调用采用结构化 **API**；路径访问检查穿越风险（如 `..`）。
- [ ] 不硬编码密钥、**AK／SK**、密码及内部 **IP**；日志不泄露身份证、手机号、**Token** 或密码。
- [ ] 鉴权、操作权限与数据权限完整；外部输入按白名单及校验规则处理。
- [ ] 加密遵守项目规范，不使用 **MD5／SHA1／DES／RC4**。

### 2.2 资源与测试

- [ ] 资源申请与释放配对，无线程、**goroutine、Promise** 或订阅、监听、缓存泄漏；**Context** 正确传递并响应取消。
- [ ] 行为改动覆盖适用的正常、边界与异常场景，保留逐行为红绿证据；非行为改动有适用检查。
- [ ] 测试断言使用独立预期，能发现真实行为错误；契约明确规定的消息可作断言。
- [ ] 集成测试使用真实 **DB**，不以 **Mock DB** 替代。
- [ ] 本次适用质量门禁通过，或例外已明确获准；不按行数或个人折行偏好阻断。

### 2.3 编码与设计

- [ ] 参考 [步骤说明建议](coding-style.md#步骤说明建议)，核对已有说明是否准确、有助于理解目的与约束；编号形式与注释数量不作门槛，一般改进按 §3 的 Nit 处理。
- [ ] 已按 [可读性与接口设计](coding-style.md#23-可读性与接口设计) 核对接口负担、表达与结构；读取实际实现及必要调用位置，不仅接受作者自检结论。
- [ ] 命名一致，必要取舍有说明；职责、分层和依赖合理，不为不存在的需求增加抽象或配置。
- [ ] 重复代码候选已核对是否属于同一业务规则，不按重复次数强制抽象。
- [ ] 错误路径、日志、链路标识和必要指标能支持排查。
- [ ] 核对 **N+1**、不必要的全表扫描及内存浪费；遵守项目框架约定，如 **go-zero** 的依赖注入与 **Context** 透传。

### 2.4 AI 生成内容核验

- [ ] 方法、字段、包、导入及错误码常量**真实存在**。
- [ ] 第三方库版本与用法符合 **go.mod、package.json、requirements.txt** 等实际依赖文件。
- [ ] 业务逻辑符合真实数据流；超时、阈值、限流等数值有依据，不凭空编造。

按场景检查国际化文案、**API** 与数据库迁移兼容性，以及 **README、ARCHITECTURE、OpenAPI** 等文档是否同步。

## 3. 审阅意见与处理

每项写清具体位置、需求或规范依据、触发条件与实际后果，记录在 **05-review.md §2「Findings（审阅发现）」**。源码行为须有实际代码依据，不凭命名或个人偏好推断缺陷。

| 等级        | 判断依据                                                                       | 处理要求                                                                  |
| ----------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 🔴 **阻断** | 本次要求未满足、有证据的功能或安全缺陷、违反现有明确强制规则，或必要验证未完成 | 修复并复验，或凭依据纠正误报；风险例外按 AGENTS §2.6 确认，未验证不标通过 |
| 🟠 **警告** | 有具体改进价值，但不影响本次要求及必要验证                                     | 记录影响及后续处理，不自动扩大当前任务                                    |
| 🟡 **Nit**  | 非强制的注释、命名、排版、可读性或重构建议                                     | 可采纳或拒绝，不阻断、不自动派生修复，也不触发新一轮审查                  |

**Nit 每次最多 5 条，不凑数。** 只报能说明具体收益的建议，跳过纯偏好和已有工具覆盖的问题。代码异味属于判断性建议；明确项目规则和真实行为风险按各自依据处理，不因模型偏好新增门槛。

同类发现合并说明问题模式与具体位置；Owner 在本 Task 范围内集中处理同类阻断项。未解决项更新原条状态及复验依据，不重复新增相同意见。实质分歧、误报纠正或获准例外在原条或 **05-review.md §4** 记录依据与决定，警告与 Nit 不因未采纳而阻断。

**结果简短、证据可追溯**：先给各级数量与结论，再列真实发现、实际验证及缺口。无问题时直说无问题，不逐项复述已通过代码；复杂问题保留修复所需的解释，不设字数硬上限。

## 4. 独立验收与合入

独立 **Review** 的返工按 [Agent 分工 §2](../agent-roles.md#2-派发与返工) 处理。审阅主体不固定为用户；项目明确要求的人工 **Reviewer**、最终审批和合入规则仍须满足，不能由 AI 替代。**修改前的审查结论不能用于修改后尚未审阅的版本**。

在 **05-review.md §1** 记录独立结论，在 **§4** 记录项目要求的审批结果及用户允许的提交操作。

按 **AGENTS.md §2.6「用户确认」** 核对操作授权及条件。独立审查通过只是提交前提之一，不代替项目审批或用户授权。

合入前须确认：**阻断问题已解决、实质澄清问题已回答、无 Security Critical 告警**，项目要求的 **CI** 门禁通过。不存在或不适用的检查不能记为已执行。

批准范围内的修正按 [验证规则](verification.md) 执行；越界、需求或 **AC** 变化、未授权副作用及必要验证缺口，按 **AGENTS.md §2.6「用户确认」** 处理。

## 5. 紧急修复（Hotfix）

仅适用于生产事故、安全漏洞或强制下线。**紧急情况不自动豁免审阅与授权**；按项目明确的紧急流程执行，没有专门约定时沿用正常门槛。

例外须说明风险、待补验证及跟进安排，经用户或项目规定的授权人确认。复盘记录在 [failures.md](failures.md)。
