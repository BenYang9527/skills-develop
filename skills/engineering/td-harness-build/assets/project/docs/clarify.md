# 澄清与独立核验

产品讨论读 **§1**；迁移或同步资料读 **§2**；开发前安排 Task 或执行开发 Clarify 读 **§3**。产品已确认，仍须完成开发核验。

**共同原则**

- **先查事实，再问决定**：按需读取 README、相关实现、测试和已有资料；不以设想证明已实现。
- **问题按依赖组织**：独立问题可一起问，有依赖的分轮讨论；说明依据、影响与建议，不限制固定提问数量或轮数。
- **争议先核对需求**：从本次 Overview 找到已确认需求和 AC，结合用户最新决定判断是缺陷、遗漏还是需求变化。不先认定实现有错，也不将需求变化当成用户接受风险；仍不明确时，只问具体缺口，不擅自增加承诺。

## 1. 产品讨论

### 1.1 Clarify：明确问题与范围

用户提出想法或需求后，直接开始本次讨论。没有产品资料时，按 AGENTS 创建；从 **00-overview.md** 定位进度，内容先写入 **01-discussion.md**。建立资料不表示需求已确认或开发已获批准。

用户无需先准备 PRD，也不必懂 User Story。通过对话明确使用者、场景、问题和目标，核对最初提出的解法是否必要；已有资料保留相关约束，不复制无关原文。

围绕本次交付逐步回答：

1. 用户完成后能做什么，希望得到什么改善？
2. 哪些 Stories 和必要依赖必须一起做？
3. 能否尽早交付有价值的结果，获得实际反馈？

范围过大时提出缩小建议，不擅自删减。一次交付可含多个 Story，共同背景与约束只写一次；不按 Story 自动建目录，不强制引入 Sprint 或 Iteration。

**本阶段完成条件**：用户确认要解决的问题及希望改善的结果。

### 1.2 Design：比较方案与原型

比较可行方案的依据和代价，解决影响选择的疑问。要求、取舍、验收条件和未决问题继续记入 Discussion，不填写正式需求、AC 或 acceptance.feature 正文。

**需要原型时**，按交付需求模板 §3 的方法明确目的，分别核对视觉和交互。AC 依赖原型的，先确认对应页面或状态；原型不能替代明确的行为和预期结果。

**原型基线**：已有页面的新设计，以当前实际页面代码为基线；此前已认可但未实现的设计继续承接，不要求保留旧原型文件。没有实际页面时，才从已有原型继续设计。

**代码复用与落地**：先引用现有组件；不方便时，只复制本次涉及的局部，不复制整个前端工程。原型认可后，开发优先移植其结构、样式和交互，再接真实数据，模拟内容按真实语义替换。

**存储与迭代**：同一交付的多个 Task 共用 **product/prototype.html** 入口，必要源码和资源放在同级 **product/prototype/**，入口记入产品 Overview，注明认可方案及基线提交。按设计需要修改或替换原型文件，旧版本由 Git 保存。新交付使用自己的目录，已结束交付的原型保留原位；依赖、构建产物和缓存不入库，不要求历史原型持续跟随生产代码更新。

**本阶段完成条件**：用户选定方案，影响选择的关键疑问已解决。

### 1.3 Confirm：整理并确认交付要求

1. **给出范围概览**：汇总重要议题，建议本轮做什么、暂缓什么，说明理由，由用户确认。已明确获准暂缓的事项可立即整理，不重复询问。
2. **整理正式文档**：用户确认讨论结论、同意整理后，统一生成 **02-delivery-requirements.md、03-acceptance-criteria.md** 和对应 **acceptance.feature** 场景。开发所需的要求必须完整写入；不新增未经讨论的承诺，发现遗漏就返回讨论。
3. **审阅确认**：用户确认范围、方案、AC 及必要原型，无影响目标或验收成立的待定项后，完成产品 Confirm。开发以正式文档为依据，Discussion 作为补充。

验收条件随需求一起讨论，不能到生成文档时才补想。AC 文件维护场景入口，行为场景使用稳定的本地 AC 编号，按产品模板编写 Gherkin 与来源说明，不重复抄写同义场景表或整篇长期规则。

上述动作属于既有产品三阶段，不新增审批阶段。只需明确本次交付，不要求先想清产品全部未来需求；模板空表也不代表需求已经形成。

Confirm 完成可以结束产品会话，不要求立即开发。产品 Overview 记录产品确认、Task 关联、依赖及完整 AC 的验证归属；开发状态和证据由各 Task 维护，不另存一份整体完成状态。

### 1.4 需求变化

新想法先讨论，不自动加入本轮：不影响当前目标的留作后续候选，影响目标成立的先确认范围调整。

用户确认变更后，更新当前需求、AC 和对应场景；比较增删改，检查对 Task、Plan 和测试的影响，重新核验受影响部分。只更新必要内容，不整篇重写；已结束的开发任务记录保留。

变更影响原确认结论、尚未获批时，将产品 Overview 的 Confirm 标为“待确认”，暂停受影响的后续工作。已有明确批准的修改，不重复询问。

## 2. 资料维护

### 2.1 各文件存什么

本轮讨论写入 **product/01-discussion.md**，保存要求、方案、理由和未决问题。以下三份产品资料默认建在 **.harness/product/**，无内容时留空：

| 文件 | 内容 |
|---|---|
| **01-prd.md** | 已确认的产品要求与必要细节，含以后开发的部分；标明实现情况，不复制讨论过程 |
| **02-backlog.md** | 待办、优先级和状态；要求详情引用 PRD，讨论详情引用讨论池 |
| **03-discussion-pool.md** | 用户确认暂缓的讨论：背景、取舍、已明确内容和未决问题；不代表需求或实施已获批 |

讨论结论确认后由主 Agent 更新 PRD、Backlog；开发交付引起的状态变化纳入 **04 Docs**，由 Owner 更新核对。状态以实际证据为准，Review 通过不等于上线。

### 2.2 讨论如何流转

- **本轮做**：留在 Discussion，按 §1.3 整理交付文档。
- **暂缓**：讨论迁入池，Backlog 登记并链接；已确认要求写入 PRD，池中只引用。
- **后续选中**：从 PRD／Backlog 定位事项，将相关池中条目迁入该轮 Discussion，复用结论、补齐缺口；仍需确认该轮需求和实施范围。
- **本轮取消**：按用户决定区分“本轮不做”和“需求不再需要”。仍需后续处理的讨论迁回池，Backlog 更新去向；明确放弃的事项在 Backlog 记录取消决定，PRD 中已有要求同步标明不再采用，不转成待办。去留不明确时请用户决定，原讨论先保留。

**迁移顺序**：保存目标内容 → 核对条件、理由和未决问题完整 → 删除源正文 → 更新受影响引用。移出本轮 Discussion 时留去向链接；池中不保留已迁出的重复正文。未迁入或核对失败的内容保留；外部删除须在授权范围内。

### 2.3 读取与更新边界

- **按问题读取**：当前要求读 PRD，选事项读 Backlog，承接只读相关池中条目；不默认读整池或旧轮次 Discussion，链接不扩大 AGENTS 规定的权限。
- **资料可独立使用**：后续所需信息须进入产品资料，不能仅链接旧任务；本轮需求与 AC 必须足以指导交付。
- **新旧冲突**：按用户最新确认决定核对，不用旧讨论覆盖新要求；产品要求变化不自动扩大本轮范围，也不回写历史交付。

### 2.4 外部资料

**入口**：本轮外部来源、相关条目和读取时间记入 Overview；三份产品资料的外部维护位置记入各自文件。

1. **核对授权**：参考资料按原意使用，不擅改；用户指定维护的位置，在获准范围内同时更新仓库和外部，无需逐次询问。
2. **更新内容**：先读双方相关内容，保持含义、决定和状态一致；保留各自格式、字段、链接及交互，不整篇覆盖。未能按已有决定解决的冲突交用户确认。
3. **报告结果**：外部不可访问或更新失败时，保留已完成的修改，报告未同步项，不宣称同步完成。

## 3. 开发准备与核验

### 3.1 读取依据

尚未创建开发 Task 时，先按 §3.3 在产品 Overview 安排任务；确认整体方案并获启动授权后，再创建对应 Task，进入开发 Clarify。只做产品时不要求开发安排。

已有开发 Task 时，按 AGENTS 定位任务，再从开发 **00-overview.md §3** 读取本轮需求与 AC。按需核对契约、长期规则和受影响代码；外部依据沿产品文档追溯，不另建入口。

核验结果写入 **01-clarify.md**：结论、依据、产品条目链接，不抄完整 AC。产品已确认，仍须独立核验。

### 3.2 核验内容

- **明确**：目标、范围与 AC 清楚。
- **可实现、可验证**：代码、契约和必要环境支持，界面 AC 的原型依据齐备。
- **无硬阻塞**：没有影响本次成立的矛盾、遗漏或未授权副作用；不穷尽未来设计。

### 3.3 安排开发任务

**划分原则**：Task 是值得独立执行、验证和收尾的实施范围。优先围绕完整用户操作划分；公共技术能力或缺陷有独立交付价值时，也可单独成任务。

Story 表达目标，AC 表达完成标准；一个 Story／AC 可由多个 Task 实现，共同约束直接关联需求章节。前后端、页面可作为 Task 内部工作块，不因此自动分成多个 Task。

**拆分前检查三点：**

1. 独立执行、验证和收尾的收益，是否值得多一套流程？
2. 每个任务依赖什么成果，具备什么条件才能开工？
3. 并行节省的时间，是否值得协调成本和相互干扰？

**确定安排：**

1. 核对相关代码、接口与已有设计，明确交付物、依赖和关键未知。影响整体方案或拆分是否成立的未知先查证，普通实现细节留待对应 Task 规划。
2. 在产品 **00-overview.md §4** 写明整体方案及 Task 安排：范围、Story／AC、所需上游成果和完整 AC 的验证责任；按 **AGENTS §2.6** 确认方案与启动授权。
3. 只创建已获授权且依赖就绪的 Task。有前置依赖时，先核对上游约定成果已合入集成分支，再进入自身 Clarify、细化当前 Plan；不预写全部后续 Plan。新证据改变安排时更新本节对应记录，超出已批准方案的变化再确认。

**验收责任**：每条 AC 指定一个负责完整验证的 Task，记入产品 **00-overview.md §4**。多个 Task 共同实现时，各 Task 在自己的 Plan 中写清自己的交付条件；负责完整验证的 Task 还须验证成果组合后的完整行为。

上游 Task 验证自身交付条件和适用的必要检查后，可以按授权提交、合入；完整 AC 仍待指定 Task 验证。局部结果不能把整条 AC 标为通过，也不属于跳过必要检查；不另增整轮验收阶段。

### 3.4 决定是否继续

**有硬阻塞：**

1. 在 **01-clarify.md** 记录问题、证据、产品原文位置及待决定事项，停止后续开发。
2. 需求或 AC 要修正时，说明原因与影响，交用户确认；不自行更改产品决定，不要求用户切换身份或新开会话。
3. 变更确认后重新核验，通过再继续。

**全部已发现阻塞解决后**，记录“无硬阻塞”，进入 **02-plan.md**。

实现中才发现需求或 AC 问题，也按上述方式停止并处理；记录原因属于既有证据遗漏、新获得事实还是外部变化，不一律认定为前置漏检。
