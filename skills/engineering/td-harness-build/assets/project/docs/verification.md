# 验证规则

> **读取入口**：Plan 选检查读 §1–2；Implement 自检读本次适用门槛及 §3；Review 读本次适用标准、§3–4。其他部分仅在当前问题涉及时展开。
>
> **命令来源**：实际工具版本与固定命令分别维护在测试、编码和环境规范中；数值门槛统一维护在本文件 §2；沿用项目入口，不让 **Agent** 每次重新找工具或拼命令。

执行角色、交接与记录归属见 [Agent 分工](../agent-roles.md)；阶段顺序见项目 AGENTS.md §2.3；语义审查方法见 [代码审阅](code-review.md)。本文件定义检查选择、通过标准和验证失败的处理条件。

## 1. 检查选择

按本次改动及风险选择检查，并在 **02-plan.md §6.4「本次检查清单」** 写明范围、执行入口、通过条件和选择依据。

| 检查                                            | 适用范围                                                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **基础检查**                                    | 每个任务执行适用的低成本检查：代码的格式、编译/类型、静态检查；文档的链接和结构                               |
| **单元测试（Unit Test，UT）、覆盖率与函数质量** | 代码改动的相关行为与回归；非行为改动不制造无意义的新测试。函数门槛见 **§2「通过标准」**                       |
| **集成测试（Integration Test，IT）**            | 改动影响真实 **DB**、上下游或组件协作时，执行相关真实依赖检查；**SQL** 查询语义变化须有有效真实 **DB** 证据   |
| **变异测试（Mutation Testing）**                | 按业务行为风险和测试有效性需要选择；纯拼写/注释不机械执行                                                     |
| **用户流程验证**                                | 影响界面和操作路径时执行实际交互，**API** 结果不代替界面验证                                                  |
| **验收测试（Acceptance Test，AT）**             | 本次 **验收条件（Acceptance Criteria，AC）** 必须验证；能证明 **AC** 的 **UT／IT** 可复用，不重复维护同义用例 |

**项目强制门禁仍须执行**，包括安全检查、**持续集成（CI）** 和 **Git Hooks**。凭证、外部输入、权限及依赖漏洞按项目基线检查；不因改动行数少而豁免，也不要求每个任务执行全部检查。

确实不涉及的检查说明原因。**工具缺失、环境不可用或未执行，不等于“不涉及”**。范围或风险变化时更新 **Plan**；超出批准范围先确认。

验收通过须有实际执行证据；读取或解析 Gherkin、查看原型不能算通过。

### 1.1 测试复用

已有 **UT／IT** 能证明某条 **AC**，且结果适用于 **当前版本、环境和范围** 时，**AT** 引用对应测试和结果。结果不再适用时重跑，仍缺少证据的 **AC** 另行验证。

### 1.2 环境准备

**测试运行设施**：Owner 在 Plan 中核实本次所需的已有入口，说明新增设施的必要性、允许范围及投入。在该范围内连续补充测试和必要设施，按实际差异更新 Plan，不逐项等待用户确认。普通 UT 的输入数据、Mock 和既有用例补充不单独审批。

- **正例（示意）**：在已有 HTTP／SQLite 测试中补失败场景，扩展现有模拟返回或共用启动函数。
- **反例（示意）**：为同一行为另建应用装配、模拟 CLI 和清理框架，未说明旧入口缺口，也未纳入 Plan。

需要部署测试版本时，优先使用项目 **CI/CD** 或已有部署入口。**发布本身属于本次目标时**，**Plan** 须写明授权、回退方式和发布后检查。

### 1.3 验证手法选择

下表按要回答的问题列出手法。本次用哪些由 **02-plan.md §6.4** 决定，并写明通过条件；没有列入手法的问题，直接按原检查结论处理。

| 要回答的问题                 | 手法             | 用在哪一步 | 要点                                                                                                                |
| ---------------------------- | ---------------- | ---------- | ------------------------------------------------------------------------------------------------------------------- |
| 声称行为不变，是否真没变     | **差分对比**     | Review     | 输入取现有测试、边界值，必要时加真实样本；预期差异先写入 Plan；只出现预期差异才算等价。对象身份与时序按契约需要比较 |
| 两版写法哪个更好             | **A/B 盲测**     | Review     | 维度先写明；隐藏来源并对调顺序；评判者用独立上下文；按理由归纳，分歧交用户。方法见 **code-review.md §1**            |
| 测试是否真能发现问题         | **变异测试**     | Review     | 由工具逐项改动实现；存活项按等价变异或覆盖缺口处置，等价项须独立核验，详见 §2 与 **05-review.md §3**                |
| 自建测量或工具是否可信       | **独立复算**     | Review     | 用另一套方法重算同一指标（另一工具或人工抽样）；全部一致，或每处差异都解释到原因，才算通过                          |
| 只改注释或格式，逻辑是否未动 | **AST 等价对比** | Review     | 仅改注释：去注释后逐字节比；改格式：按语法树逐节点比，忽略位置                                                      |
| 规则或工具声称能防某问题     | **对抗用例**     | Review     | 主动构造绕过写法（等价改写、移入回调、间接调用）；未被暴露的绕过记为工具缺口，写入规则说明，撤回对应的覆盖声明      |

“行为一致”与“哪个更好”是两类问题，不能互相替代；自评不算盲测。

## 2. 通过标准

下表是新项目默认值。已有项目的明确门槛继续保留，冲突先确认，**不得检查失败后自行降低门槛**。列出标准不代表工具已经接入。

| 检查项                                     | 默认通过条件                                           | 范围/说明                                                           |
| ------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------------- |
| **圈复杂度（Cyclomatic Complexity）**      | ≤10                                                    | 新增／修改函数；确认工具按“超过 10”判失败，而不是“达到 10”判失败    |
| **认知复杂度（Cognitive Complexity）**     | ≤15                                                    | 新增/修改函数                                                       |
| **CRAP**                                   | ≤10                                                    | 使用同版本有效 **UT** 覆盖数据；100% 覆盖时 **CRAP** 仍等于圈复杂度 |
| **嵌套深度（Nesting Depth）**              | ≤4 层                                                  | 新增控制结构；不因历史已有超标而扩大清理                            |
| **UT 覆盖率（Code Coverage）**             | ≥80%，关键行为测试有效                                 | 本次改动范围；不能用全仓平均掩盖当前缺口                            |
| **变异测试（Mutation Testing）**           | 选定范围内有效变异被测试发现，无未处置的未覆盖或存活项 | 等价变异可凭证据经独立核验排除；执行错误不算检测成功                |
| **重复代码（Code Duplication）**           | 工具标出的重复片段已处理，或有经独立核验的保留理由     | 结构相似不等于业务规则相同，不设零重复率或按次数强制抽象            |
| **架构依赖（Architectural Dependencies）** | 无禁止依赖方向或循环                                   | 依赖数量仅作观察，语义分层仍由独立审查核对                          |

变异检查的执行与缓存处理按项目测试规范，保留工具原始清单，不手改工具清单来隐藏问题。

### 2.1 超标处理

新增代码按门槛修正；历史问题记录基线，**本次引入或加重的问题须处理**，不扩大为无关重构。

先核对测试、输入数据和实际代码结构，再决定改法。**不为降分机械拆函数、制造抽象或弱化断言**；例外按授权规则确认，不以反复申请例外代替修正。

### 2.2 旧代码重构

**重构旧代码前须取得用户同意**；同一方案已有明确批准时，不重复询问。申请时说明具体问题、改法、影响范围，以及如何验证行为不变（可用 §1.3 差分对比）。

默认用短文字和必要代码示例说明；结构难以表达时再加图，不强制图片、**HTML** 或额外文档。完成后，将实际变化与验证结果写入当前阶段记录并汇报。

## 3. 执行与复验

### 3.1 执行顺序

**Implement：逐行为执行测试驱动开发（Test-Driven Development，TDD）。**

跑红 → 最小实现转绿 → 必要时最小重构并复测 → 下一个行为。

重构须保持行为不变并遵守授权，边界见 [TDD 规范](testing/tdd.md#循环规则)。Plan 先列用例，不等于先写完全部测试。

**Review：按 Plan 执行所选检查。**

- **先做基础检查**：执行基础与复杂度检查。
- **CRAP 的前提**：UT 成功并生成同版本有效覆盖数据后，才能计算 CRAP。

IT、AT、变异测试及 §1.3 选用手法按 **Plan** 安排执行；A/B 盲测由 Review 执行。**高风险技术或环境先探测**，不机械按耗时排序。

### 3.2 证据记录

在 **05-review.md** 记录版本、实际命令、必要数值和关键原文。输出留在终端，不要求另建报告；覆盖率文件和工具临时产物按需使用。

| 检查     | 需要保留或核对的证据                                           |
| -------- | -------------------------------------------------------------- |
| IT       | 关键日志及适用的 reqid／trace                                  |
| UI       | 实际操作与结果                                                 |
| 变异测试 | 逐项核对结果，不能只看退出码或总百分比                         |
| 重复检测 | 实际扫描范围、原始报告及失败原因；工具与命令见 coding-style.md |

记录与当前检查有关的证据，不贴无关全量日志，也不只写链接或“符合预期”。重复检测命令成功，不代表重复问题已处置或 Review 已通过。

**函数质量检查范围**：优先使用可靠的增量筛选；不支持时，在相关模块全量计算，再对照 **git diff** 确定新增／修改函数，并独立核验。

### 3.3 检查无法完成

**结果与缺口**：区分 **通过、失败、未执行、不涉及**。失败命令须保留失败状态，不能被后续 **echo**、**SKIP** 或成功命令覆盖。缺少工具或环境时，报告缺口、准备方法和重跑命令。

**推进条件**：必要检查未完成时停止后续推进；用户明确同意跳过后，在 **05-review.md** 记录未验证项、原因及剩余风险，仍不标为通过。下述 UI 工具故障可直接按约定继续文档与审查，无须逐次申请跳过。

**UI 工具故障**：有证据确认 **computer-use／browser-use 不可用、连接或窗口获取失败、工具调用超时**，导致实际 UI 操作未完成时，先做有限恢复；相同故障重复且没有新依据时停止重试。**其他必要检查已满足原有推进条件**，即可按顺序继续 **Docs → Review**。产品响应超时、交互断言失败或原因不明时先调查，不自动适用此安排；已确认产品缺陷仍返回修复。

**记录与补验**：

- 在 **05-review.md §4** 记录“**UI 待补验证，审查可记录但验收未通过**”，列明受影响 AC／操作、故障证据、已尝试的恢复、补验责任与恢复条件；**Overview** 保留待验证状态。文档只写已有证据支持的事实，UI 不标为通过、不涉及或已跳过；阶段仍按顺序推进。
- **UI 待补时不完成整体验收、不将 Task 标为完成、不进入 Submit**。Review 可先完成代码与文档审阅，结论保留“**待 UI 验证**”。
- 工具恢复后，由同一独立 **Reviewer** 补做缺少的实际界面操作及受影响复验，并核对差异后给出最终结论；失败交 Owner 修复，仍有效的结果不重复执行。

### 3.4 修正与复验

**需用户决定的阻塞立即报告，不等整轮结束。** 其余问题在一轮检查后按以下顺序处理：

1. **汇总问题**：核对证据与授权。
2. **批量修正**：批准范围内连续处理，不逐次询问。
3. **独立复验**：重验受影响项；未受影响的证据按 §1.1「测试复用」引用。

在 **05-review.md §3「实际验证」** 保留首次失败、原因、修正和复验结果。

## 4. 独立验收与授权

### 4.1 Review 核对内容

按 **[code-review.md](code-review.md)** 独立核对需求、规则、设计与交付证据，不默认重跑全部检查，不另设数值门槛。

- **语义问题**：给出位置、规则和理由，不凭“太长”或“感觉不好”阻断。
- **测试质量**：核对独立预期、有效断言及 AC 覆盖，不能只看覆盖率。
- **架构指标**：工具能准确检查的项纳入固定入口，不重复手抄指标。

> 示例：可复用的无状态业务转换函数放在 RPC Logic，违反项目的 helper 分层约定；即使测试通过，仍须纠正。

### 4.2 审查与提交衔接

**审阅与复审**：方法及修改后复审要求见 [code-review.md §4](code-review.md#4-独立验收与合入)，实际结论写入 **05-review.md §1**。

**提交授权**：提交前按 **AGENTS.md §2.6「用户确认」** 核对审批与操作授权。检查通过不代表已获准提交。

**需求或 AC 有误**：按 **AGENTS.md §2.3.4「反馈与返工」** 返回对应阶段，不通过修改 AC 掩盖失败。
