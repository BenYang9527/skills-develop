## 4. Review Findings（审阅发现）

按 **.harness/docs/code-review.md** 判断问题及严重度。每项写明具体位置和需求、规则或风险依据；未发现问题时写“无”。

| #   | 严重度              | 文件／行号 | 问题描述及依据 | 建议 | 处理状态                         | 复验／复审依据 |
| --- | ------------------- | ---------- | -------------- | ---- | -------------------------------- | -------------- |
| 1   | 🔴 高／🟠 中／🟡 低 |            |                |      | 待处理／已修复／不采纳／批准例外 |                |

**不因工具通过就忽略分层错误或无效断言，也不凭“太长”“更优雅”阻断。** 不采纳或批准例外的理由记入 **§5「讨论与决议」**；修复项填写复验／复审依据。

## 5. 讨论与决议

记录审阅意见存在分歧、不采纳或申请例外时的决定及依据。普通修复记录在 **§4「Review Findings（审阅发现）」**；本节不重复。

| #   | 议题 | 讨论 | 结论 | 决策人 |
| --- | ---- | ---- | ---- | ------ |
|     |      |      |      |        |

修正后，重新检查受影响的部分并交独立 Reviewer 复审，不能沿用修改前的通过结论。

如果用户原先说过“满足这些条件后可以提交”，还要核对修改后是否仍满足这些条件。超出批准范围或需要改变 AC 时，按 **AGENTS.md §2.6「用户确认」** 处理。

## 6. 复盘

检查本轮是否出现值得记录的失败；判断范围及复盘方法见 **.harness/docs/failures.md**。重要失败由 Owner 登记到该文件；Reviewer 核对登记内容，本节只记录结论与链接。

- **复盘结论**：无重要失败／已记录。
- **失败记录链接**：

提出改进建议不代表已经实施。修改 Harness 须在已有授权范围内；超出范围时，按 **AGENTS.md §2.6「用户确认」** 处理。

## 7. 最终结论与授权核对

- **独立 Review 结论与最终审查版本**：
- **未解决问题与已批准例外**：引用 §4、§5 对应记录。
- **项目要求的审批与结论**：项目要求人工审批时写明审批人、范围和版本；不涉及时说明依据。
- **Submit 授权来源与范围**：填写实际获准的操作，如 commit、push、创建 PR。
- **用户要求的提交条件**：例如“检查和审查通过后可以提交”。逐项记录当前版本是否满足；没有额外条件时写“不涉及”。

按 **AGENTS.md §2.6「用户确认」** 核对并填写以上各项；缺少审批、授权或条件未满足时，记录具体等待项。

## 8. 完成检查

提交后返工时，以下记录更新项按 **06-submit.md §4** 的冻结范围执行。

- [ ] Plan 所选检查及 AC 有当前版本证据，未验证项与环境收尾已记录
- [ ] 独立 Reviewer 已核对实际改动、接口与代码可读性、项目规则及验证充分性
- [ ] 阻塞问题已修正复验，其他问题有明确处置
- [ ] 重要失败已复盘并登记入口；没有则写明无重要失败
- [ ] 独立结论、项目要求的审批及 Submit 授权已分别核对，缺少授权或条件未满足时已说明等待项
- [ ] Owner 已更新 **00-overview.md** 的开发进度与时间记录，Reviewer 已核对；Reviewer 的写入范围仍按 agent-roles.md §1.1 执行

独立审查通过、项目要求的审批完成且有效授权条件满足后，进入 **06-submit.md**，仅执行已授权操作。
