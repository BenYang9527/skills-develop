# 07. Submit

> **执行角色**：Executor；派发与权限见 **.harness/agent-roles.md**。
> **用途**：按用户授权提交代码、推送远端或创建 PR。
>
> **前置条件**：Verify 已完成必要检查，Docs 已按需更新，独立 Review 已通过，项目要求的审批已完成，待执行操作在用户批准范围内，用户提出的执行条件也已满足。
>
> **提交策略**：默认一个 PR 对应一个 commit（one-PR-one-commit）；后续修正按 §4 amend 流程处理。项目另有明确约定时，按项目规则执行。
>
> **授权核对**：执行前按 **AGENTS.md §2.6「用户确认」** 核对本次操作及条件，在 §1 记录依据。Git 操作仍须遵守项目保护分支规则；禁止裸 `--force`。

## 1. 前置检查

### 1.1 分支与基线

- **当前任务分支**：
- **目标集成分支**：填写实际分支引用。
- **整理基线**：填写目标引用更新并核对后的提交 SHA。

**SHA 是 Git 的提交编号。** 分支名指向的提交会变化，用 SHA 固定本次采用的版本；由 Agent 从 Git 读取。任务创建起点与工作目录对应关系见 **Plan §1**。

### 1.2 验证、审阅与授权

| 核对项 | 记录内容 |
|---|---|
| Verify 依据 | 引用 04-verify.md，确认结论适用于当前待提交内容 |
| Review 与项目审批 | 独立审查结论、审查对应的版本，以及项目要求的审批结果 |
| 本次操作授权 | 实际获准的 commit／push／PR、用户批准依据，以及约定条件是否满足 |
| 环境释放／部署／集成测试 | 不涉及／已处理／未验证；未验证时记录明确决定 |

### 1.3 历史与内容范围

- **已有历史**：是否已推送，有哪些内部 commit／merge。
- **本次内容**：基线到最终内容的差异是否都属于本任务，无关工作如何保留。
- **整理前的恢复位置**：记录未占用的本任务恢复分支，按 §2 创建；不整理历史时说明不涉及。

恢复依据须能找回已审版本和整理前历史，具体处理见 **§2**。

### 1.4 核对后再整理

1. **确定基线**：更新目标集成分支引用，核对本次采用的提交。不能直接用任务最初的分叉点或自动算出的 merge-base（共同祖先提交）代替。
2. **处理目标分支变化**：有需要纳入的变化时，先合入任务分支，再补做受影响的检查和审查。
3. **核对历史与范围**：确认基线提交是当前 HEAD（分支当前提交）的祖先，并逐项核对基线到最终内容的差异。祖先关系正确，不代表改动范围正确。

**基线不明、夹带他人提交或无法保留无关工作时，停止整理并报告。**

验证后交付内容发生变化，须补做受影响的验证与审查，并更新相应记录；失效结果不能继续使用。

**预登记**指提交前补齐 §2 约定的任务记录。逐项核对这些记录差异，仅本阶段允许且已获准的正常预登记差异可直接继续；不能夹入实现修改。

## 2. 执行顺序

| # | 动作 | 执行要求 |
|---|------|----------|
| 1 | 编写 commit message | 填入 **§3「Commit Message（提交说明）」** |
| 2 | 预登记任务完成 | 更新 **00-overview.md** 的时间记录 07 行结束时间与耗时、Meta 状态、关键决策；开发进度的 07. Submit 标为已完成（预登记） |
| 3 | 暂存与内容比较 | 使用明确文件路径执行 `git add`，包含本次代码、任务记录和相关文档；逐项核对相对已审版本的差异，只有获准预登记差异可直接继续 |
| 4 | 创建或整理 commit | 保留已审版本及整理前历史的可恢复引用，按下方条件整理为本任务一个 commit；比较最终内容与已核对暂存内容 |
| 5 | 推送／创建 PR | 再核对目标引用、授权与内容；仅执行获准操作，向用户报告实际结果 |
| 6 | 处理后续修正（发生时） | 按 **§4 amend 流程**处理，完成范围内修正、受影响验证与复审，并更新尚未冻结的相关记录 |
| 7 | 获准合入后的清理（发生时） | 核对实际合入结果、成果保留及目录安全后普通清理；不确定则保留并报告，不阻塞已成功的交付 |

**预登记不代表提交成功**：push、PR 合入和上线结果以实际 Git／平台状态为准，另向用户报告；操作失败不能报完成。

**以下命令只在当前任务分支执行。** 使用 soft reset（保留暂存内容的提交回退）整理历史前，必须确认：用户已批准本次历史整理、基线和改动范围已核对、暂存区包含完整的最终交付内容。

尚无内部提交时，直接创建 commit；已有最终提交的修正按 §4 处理，不套用下面的历史整理步骤。

已审查的提交不是当前 HEAD 时，先用一个未占用的恢复分支保存该提交。如果审查的是未提交的工作区内容，也须能准确找回当时的内容，不能拿未经核对的 HEAD 代替。

命令中的变量取自 **§1** 已核对的记录：

- **integration_ref**：更新后的目标分支引用。
- **task_base**：本次采用的目标提交 SHA。
- **recovery_branch**：尚未占用的本任务恢复分支名。
- **commit_message_file**：实际提交说明文件。

先用明确路径暂存本次文件，并与已审查内容比较。已跟踪文件不能留有未暂存修改；无关、未跟踪和忽略文件不自动加入提交。

```bash
git status --short --untracked-files=all
git diff --cached --stat
git diff --cached --check
git diff --exit-code
test "$task_base" = "$(git rev-parse --verify "$integration_ref^{commit}")"
git merge-base --is-ancestor "$task_base" HEAD

# 保存整理前历史；暂存内容包含逐项核对后的正常预登记差异
git branch "$recovery_branch" HEAD
expected_tree=$(git write-tree)

# 仅在上述条件全部满足时整理本任务历史
git reset --soft "$task_base"
git commit -F "$commit_message_file"

# 检查提交钩子后的内容与单提交结构
git diff --exit-code "$expected_tree" 'HEAD^{tree}'
git rev-list --count "$task_base..HEAD"
git status --short --untracked-files=all
```

逐条执行，检查成功才继续；提交数必须为 **1**。内容比较或提交钩子失败时保留现场并停止推送，不用 hard reset 丢弃现场。推送前按项目方式刷新并再次核对目标引用，变化则停止并重新核验；已推送历史的整理还须有效 push 授权，按 §4 的 `--force-with-lease` 规则执行。

**合并到集成分支须另获批准。** 根据 Git 或平台的实际结果，核对集成分支包含哪些成果，以及下游应从哪个版本开始。squash（压缩合并）会改变提交历史，不能只看原提交是否仍是祖先。

清理前，运行下面的命令查看工作目录：

```bash
git -C <工作目录> status --short --untracked-files=all --ignored
```

确认已跟踪、未跟踪和忽略文件中需要保留的内容都已保存；没有进程仍在使用目录，目录也确实属于本任务。确认后再普通移除工作区并删除临时分支：

```bash
git worktree remove <工作目录>
git branch -d <临时分支>
```

**普通删除被拒绝时，保留现场并检查，不改用强制删除。** 有未保存内容、归属不明、仍被占用的目录，以及尚未核对成果的恢复分支都保留。无法证明清理安全时，报告保留项；不能因为 squash 改变了祖先关系就强删。


**边界点 A**：完成步骤 1、2 后，**00-overview.md** 和本文件冻结。

**边界点 B**：PR 合入后，任务冻结。

## 3. Commit Message（提交说明）

```text
<type>(<scope>): <subject>

<body>
```

按项目提交规范填写；需要关联事项时，在末尾添加 `Closes #123` 或 `Refs #123`，不要将占位内容和填写提示写入实际提交。

允许类型：

`feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert|other`

## 4. amend 流程

**恢复预登记后的任务**：先核对 Git／平台实际结果，再按问题读取本任务 **03–06** 的返工记录、未完成检查及相关工作区差异。尚未合入时，有修正、复验或复审未完成的，先回对应阶段；没有返工、仅提交操作未完成的，才续做获准 Submit。缺少证据时先核实，不凭 Overview 的“已完成”跳过返工。

返工开始时，在对应的未冻结阶段记录问题、待办和完成情况；处理后更新结果。**00-overview.md** 和本文件仅作为冻结的恢复依据，不回写新状态。PR 已合入的，按 AGENTS 的已结束任务规则处理。

已有本任务 commit、PR 尚未合入，且修正完成验证与复审后，按以下命令更新原提交；命令保留原 commit message，需要调整说明时去掉 `--no-edit`。

```bash
git add -- <本次批准的文件>
git commit --amend --no-edit
# 仅已推送且 push 授权仍有效时：
git push --force-with-lease
```

> 修正限于批准范围，并将本次修正和复验／复审证据更新到尚未冻结的 **03-implement.md、04-verify.md、06-review.md**；受影响的文档更新记录写入 **05-docs.md**。**00-overview.md** 和本文件按边界点 A 保持冻结，实际提交结果向用户报告。PR 合入后按边界点 B 冻结整套任务记录。需要改变需求或 **02-plan.md** 时先停止处理，不借 amend 扩大范围。

## 5. 完成检查

- [ ] **提交说明**：Commit Message 与本次实际改动一致。
- [ ] **任务记录**：00-overview.md 已按 §2 完成预登记。
- [ ] **实际提交**：基线有效，最终为一个 commit，且只包含本次批准的文件与改动。
- [ ] **恢复与比较**：按 §1、§2 确认已审版本和整理前历史可以找回；最终内容与已审内容的差异已核对。
- [ ] **内容变化**：正常预登记差异已单独确认；其他内容变化已完成受影响的验证与复审。
- [ ] **推送与 PR**：获准操作已成功；未获准的操作明确记为未执行。
- [ ] **合入结果（获准合入时）**：已核对集成分支实际包含的成果。
- [ ] **清理结果（获准合入后）**：安全清理已完成，或已说明保留的工作区／分支及原因。

冻结后按本清单核对实际结果并向用户报告，不回写冻结文件。**预登记不是 commit、push 或 PR 操作成功的证据。**
