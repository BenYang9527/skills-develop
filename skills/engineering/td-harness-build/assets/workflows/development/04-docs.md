# 04. Docs

> **执行角色**：Owner；派发与权限见 **.harness/agent-roles.md**。
> **用途**：同步本次改动影响的文档，记录更新内容与核对结果。
> **填写范围**：仅记录文档影响、文档改动、一致性核对及完成情况。不得新增章节或写入其他执行过程；核验和审阅结果链接对应记录。
>
> **方法入口**：使用本模板；只读取本次文档影响命中的 **AGENTS.md Index** 专题章节，不遍历整个索引。任务副本引用原模板后，仍从 **.harness/templates/development/04-docs.md** 读取维护方法。
>
> **本轮依据**：对照最终代码、**02-plan.md、03-implement.md** 及已执行的检查证据；无长期事实变化时说明原因。独立验收反馈涉及文档时，在本记录补充修正，并在 05-review.md 记录复核结果。

## 1. 文档影响检查

先按下表判断本次影响，再通过 **AGENTS.md Index** 及相关专题定位实际文件。README、用户指南和 CHANGELOG 按项目实际位置核对；不涉及的项注明原因。

逐项核对受影响文档，避免只改代码，或只改一份文档而遗漏相关说明。文档与代码保持同次交付，不强制另开 docs PR。

**文件边界**：Docs 阶段只能更新已有长期文档，不得新增文件，也不申请新增文件例外。按已有文件职责归入内容；没有专门文件时，使用职责最接近的已有文件，不另建模块说明。此限制不改变产品和开发任务按模板创建的流程。

新增能力所需的专题文档尚未建立时，记录缺口，交主 Agent 在已授权的建设或升级范围内补齐；补齐前不标记文档完成。

| 本次变化                                    | 需要核对的内容                                                |
| ------------------------------------------- | ------------------------------------------------------------- |
| ⬜ 模块、调用链或并发模型变化               | 系统架构说明                                                  |
| ⬜ 依赖或拓扑变化                           | 上下游说明                                                    |
| ⬜ 接口、字段、契约路径、service 或路由变化 | 契约定义及注释、接口索引；字段或接口语义变化还须核对变更历史  |
| ⬜ 数据库用途、关系、约束或文档链接变化     | 数据库说明与结构来源                                          |
| ⬜ 测试约定、命名或 Mock 策略变化           | 单元测试规范                                                  |
| ⬜ 环境、配置、启动或调试方式变化           | 本地开发说明                                                  |
| ⬜ 发布、检查或恢复方式变化                 | 发布与恢复说明                                                |
| ⬜ 功能实现情况或需求处理状态变化           | PRD、Backlog；指定外部维护位置时，按项目 clarify.md §2.4 同步 |
| ⬜ 用户可见的变化                           | 项目实际 README／用户指南                                     |
| ⬜ 项目版本记录约定要求更新                 | 项目实际 CHANGELOG                                            |

产品说明按项目已有文档职责维护，核对来源与时间；改图后检查渲染，未核实内容标明“待核实”。未实现计划不写成现状，已结束的需求和开发任务记录不续改。

接口说明及历史记录按 **contracts/index.md、contracts/change-history.md** 核对。

> eg:（反例）新增字段后只改代码，或只改契约，却遗漏接口索引、字段变更历史及受影响的调用链说明。

### 1.1 证据与事实

用 **rg --files** 定位依据，只读取本次变化涉及的内容。

| 要说明的内容 | 核对依据                 |
| ------------ | ------------------------ |
| 产品现状     | 已确认且已实现的能力     |
| 架构与上下游 | 入口和实际调用           |
| 接口         | 真实契约及注释           |
| 存储         | Migration / Schema / ORM |
| 命令         | 项目脚本、锁文件和 CI    |

**事实与意图分开**：标明当前事实、已确认但未实现的意图、待确认项。未接入、不适用、未知和读取失败分别说明；不补造结构、环境、原因或日期。

**结论以证据为限**：命令存在不代表已经执行，配置支持部署不代表已经上线。

### 1.2 内容与职责

**保留与归档**：权威说明只保留一份，其他位置放摘要和链接。保留有效项目规则、人工内容和历史；现行说明写当前职责与操作，淘汰方案和讨论经过留在历史。冲突按项目确认规则处理，不自行启动旧文档迁移。

**更新方式**：人工说明依据源码和配置作最小修正；确定性产物修正生成源后重新生成，优先复用已有工具。不为写文档另造抽取器，也不要求人工说明字节级相同。

**授权边界**：文档维护不自动授权修改源码、契约、Schema 或配置，也不授权安装、启动服务、数据库访问、外部写入、部署或发布。发现这些缺口时报告主 Agent，按已有授权安排修正；执行前核对权限与副作用，仅执行已授权操作。缺工具或环境时，记录原因和待验证条件，不标通过。

**记录位置**：固定命令放编码或测试规范，数值门槛放 **verification.md**。自测证据记入 03-implement.md，文档更新记入本文，独立验证与审查记入 05-review.md。

各文档首次引入流程缩写时写明中文与英文全称，后文使用简称。

## 2. 改动明细

写明具体变化及影响，不用笼统结论代替改动说明。

> eg:（反例）只写“修复 bug”或“优化性能”，读者无法知道行为发生了什么变化。

| 文档 | 路径 | 改动类型 | 改动说明 | 状态 |
| ---- | ---- | -------- | -------- | ---- |
|      |      | 修改     |          | ⬜   |

> 状态：⬜ 待更新 \| ✅ 已更新 \| ➖ 不涉及

## 3. 一致性核对

按本次文档变化核对关键说明与最终代码、契约或配置是否一致，保留具体依据；不只检查链接有效，也不在本文件复制字段定义。

核对 Docs 阶段没有新增长期文档，并检查内容归属、重复和事实一致性；放置不合理时直接调整到合适的已有文件，复核后继续，不把新增文件的选择交给用户。

### 3.1 事实与局部日期

逐项核对本次受影响事实：接口名称、默认值、注释与兼容性依据一致，命令及配置入口确实存在，图与代码一致且可以渲染。可执行且已授权的入口须实跑；已有有效证据可按项目现有验证规则复用，并记录依据。实际执行的命令记录结果与时间；缺工具、缺环境或其他未执行情况说明原因与缺口，不能标通过，不因此扩大授权。

**Source / Last-verified** 只覆盖实际扫描或核验的内容。局部更新时标明章节或条目与核验范围，保留其他内容的原日期，不给未核验内容统一刷新时间。

### 3.2 索引与引用

逐行核对 **AGENTS.md Index** 中本次受影响的主题、实际文件、读取时机及章节引用；入口和项目专属规则变化时同步索引。接口主题指向真实契约；已有 Hook、CI、治理及测试规则保留可定位入口。索引只保留跨任务导航，具体任务按 Workflow 恢复，不登记任务链接或进度。

移除已失效且不适用的索引项，保留原任务与历史文件；必要资料缺失标“待补齐”并报告，不写成可用链接，也不为凑索引新增文件。保留“何时读取、主题、文件”三列及主题加粗格式；低频子文档由对应主题继续链接。

| ------ | -------------- | -------- |
|        |                |          |

> eg:（示例）文档说明“参数嵌套最多 6 层”；对照实现中的深度上限及判断逻辑，记录一致或具体差异。

## 4. 完成检查

提交后返工时，以下记录更新项按 **06-submit.md §4** 的冻结范围执行。

- [ ] 受影响文档已更新；不涉及项已说明原因。
- [ ] Docs 阶段未新增长期文档；内容归属、重复及事实一致性核对已通过。
- [ ] **00-overview.md** 的开发进度与时间记录已更新。

完成后按 **AGENTS.md §2.3** 继续；交接按 **.harness/agent-roles.md §2**，用户确认要求见 **AGENTS.md §2.6**。
