# 03. Implement

> **执行角色**：Coder；派发与权限见 **.harness/agent-roles.md**。
> **用途**：在已授权范围内按 **[02-plan.md](02-plan.md)** 实现代码，记录关键处理、计划差异与检查结果。
>
> **方法**：行为改动按 **02-plan.md §6.2** 逐用例执行测试驱动开发（Test-Driven Development，TDD）的红绿循环；测试边界见 **.harness/docs/testing/tdd.md**，检查方法与授权边界见 **.harness/docs/verification.md**。

**先按改动性质读取：**

- **行为改动**：读取 §3.1 与项目 TDD 规范，在已授权范围内按 Plan 实现和验证。
- **纯文案、注释等非行为改动**：按 Plan 的检查范围执行，记录在 §3.3；不为确认 TDD 例外而读取整篇 TDD，也不强制新增测试。无法确定是否改变行为时，先核对需求、差异及相关代码。
- **内部并行**：安排了工作块时，读取 §1 的汇合说明和流程图；没有并行时直接记录本次实现要点。

## 1. 实现要点

逐文件记录**关键实现细节**：为什么这么写、遇到的问题及特殊处理。不复制代码，不重复 Plan。

按 **Plan §1** 登记的工作安排和代码目录实现。安排内部并行时，按以下分工执行：

- **各工作块**：在自己的 worktree 中实现并自检；行为改动按 TDD 推进，其他检查按 Plan 执行。报告本块的改动、检查证据和未解决问题。
- **主控**：核对各块结果，按批准范围普通 merge 回任务分支，汇总到同一套 Task 记录，并按 §4 核对整个 Implement 阶段的完成条件。

记录保留证据链接，不复制全部日志。合并文档时仍须核对内容，**Git 没报冲突不代表记录正确**。

工作块的阶段边界按 **.harness/agent-roles.md §1** 执行；返工派发与会话续接按该文件 §2 执行。

## 3. 实现过程检查

### 3.1 红绿证据

**行为改动**：按 Plan 的单元测试（Unit Test，UT）用例，先运行测试并确认目标行为失败（Red），再以最小实现使其通过（Green）；逐行为推进，已有测试保持通过。

测试转绿后，仅针对本次改动中的具体代码坏味道或规范违规，按授权范围做最小重构（Refactor），保持行为不变并重跑受影响测试；无具体问题则记录“无需重构”。**非行为改动**写“不涉及 TDD”，按 Plan 的验证命令执行并在 §3.3 记录结果。

| Plan §6.2 用例 | Red 命令与目标行为失败的关键输出 | 最小实现及 Green 命令 / 结果 |
|---|---|---|
|  |  |  |

**禁止为通过测试而弱化断言或修改业务契约。** 测试失败时，先核对需求、验收条件（Acceptance Criteria，AC）与独立预期；批准范围内的问题修正后复验，越界或需求 / AC 有问题时停止并确认。

### 3.2 代码自检

**通用**

- [ ] 无硬编码凭证 / Token / 密码
- [ ] SQL 全部参数化，无字符串拼接
- [ ] 外部输入均有校验
- [ ] 错误路径有日志，包含上下文
- [ ] 关键路径有指标 / trace 埋点
- [ ] 无死循环 / 无边界递归

**并发 / 性能**

- [ ] 共享状态有锁或无状态化
- [ ] 长循环是否让出调度（协程项目必查）
- [ ] 不在请求处理中做 O(n²) 以上的计算
- [ ] 外部调用有超时设置
