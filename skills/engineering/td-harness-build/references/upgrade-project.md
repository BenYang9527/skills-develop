# 升级与内容保留

> 初始化或更新已有项目时读取。目标是可用的项目规则；文件复制、目录改名和链接创建只是准备动作。

## 1. 确认目标与范围

明确本次项目目录，读取现有入口、配置和未完成任务。多项目仓库的共享入口只管共识与导航，各项目维护自身规则；Git Hook 位于仓库级，命令必须指定正确工作目录。

仅执行本次已授权的操作。文档适配、最小工程和工具接入按 **[SKILL.md](../SKILL.md)** 的边界推进；不修改安装目录，不顺带提交或发布。

## 2. 按内容归属更新

| 对象 | 默认处理 |
|---|---|
| 缺失的长期资料 | 复制对应骨架，再填已核实事实 |
| 已有项目资料、规则与配置 | 保留并比较，按授权融合独有内容 |
| 本 Skill 的标准 Workflow 及工作流模板 | 更新标准章与当前模板；先保留章内项目独有规则，项目新增模板保留 |
| 已建立的产品或开发任务 | 保留原目录、阶段和历史，不套新编号重写 |
| 模型、Hook、工具专属配置 | 保留实际入口，按批准范围修改，验证是否生效 |

模板中的 **PROJECT-CONTENT** 标记以下为项目内容。旧文件无标记，或在标记上方含实际项目内容时，同样保留；不能根据位置判定可覆盖。不要给整个旧文件做一次性替换。

项目规则与新默认规则不一致时，说明差异及影响；已能依用户决定解决的直接处理，尚无依据的交用户选择。不要为统一外观删除有效约束。

## 3. 迁移到当前目录

### 3.1 目标位置

| 内容 | 位置 |
|---|---|
| 长期工程资料 | **.harness/docs/** |
| 产品资料 | **.harness/product/**：01-prd.md、02-backlog.md、03-discussion-pool.md |
| 本轮工作与记录 | **.harness/plans/** |
| 可复制模板 | **.harness/templates/** |

新产品模板包含 **00-overview.md、01-discussion.md、02-delivery-requirements.md、03-acceptance-criteria.md、acceptance.feature**。新生成不创建 product-state；已有内容先确定归属，再按授权融合。

### 3.2 迁移步骤

1. **列清差异**：记录旧位置、目标位置、独有内容和受影响引用，明确本次批准范围。
2. **备份原件**：保存原入口、同名定制模板和历史任务，核对备份与原件一致。
3. **隔离生成**：升级已有项目时，只在隔离目录运行构建脚本。旧布局的提示和授权处理见下方说明。
4. **融合候选**：比较新模板与原件，保留项目独有规则；字段定义仍引用契约或 Schema。架构现状按代码核对，已确认但未落地的选型保留并标明。
5. **审查并应用**：核对差异、完成审查后，按批准范围应用到实际项目。应用前原项目和历史任务保持原样。
6. **修复引用与清理**：核对受影响链接；只有融合完成、引用修复且删除获准后，才移除冗余旧入口。

**脚本提示与处理**

| 情况 | 结果与处理 |
|---|---|
| 检测到旧路径，未传 --accept-migrations | 输出 **[MERGE]**，退出码 **3**，不写目标 |
| 获准后传入 --accept-migrations | 允许准备新布局；旧文件和历史任务仍保留，不自动融合语义，不代表迁移完成 |

检测范围包括旧产品模板 **.harness/templates/product/** 下的 **01-requirements.md、02-acceptance-criteria.md**，以及 **.harness/docs/product-state/**。

**生成限制**：脚本会刷新同名模板和标准 Workflow。稳定性检查在尚未融合定制的隔离目录完成；融合后不再用脚本覆盖候选或原目标。

例如，自有 **00-overview.md** 的确认规则须从原件合入候选，再审阅差异；不能先覆盖原件再找回定制内容。

### 3.3 特殊内容的保留

- **长期资料**：产品现状、运行说明、测试规范和数据库说明按各自职责融合，不因目录调整丢失有效内容。
- **任务记录**：旧任务按原 Overview 和阶段文件恢复；新任务使用当前产品或开发模板。不移动已结束任务来追求目录一致，也不改写历史执行事实。
- **角色专题**：将旧 **.harness/agents.md** 融合到 **.harness/agent-roles.md**，保留项目职责、权限约束和有效接入摘要；同步入口、阶段模板、任务链接及原生角色配置引用。脚本只提示并保留原件，删除条件同 §3.2 第 6 步。

## 4. 入口与平台配置

### 4.1 规则入口与导航

先读已有 AGENTS.md、CLAUDE.md 等入口。相同规则只维护一份，平台特有内容留在对应入口；适合时再创建软链，不直接替换已有文件或软链。

按 [入口生成指令](init-agent-entry.md#2-按证据填充) 核对内容归属。标题和规则应清楚可定位；详细内容下沉专题，入口保留必要授权与项目约束。

**清理 Index 时，只移除具体任务的索引行。** 保留跨任务入口、项目专属规则，以及原任务目录、日期、阶段记录和恢复规则。链接有效不等于应留在 Index，保留历史也不等于保留错放的导航。

### 4.2 原生 Agent

按 [agent-setup.md](agent-setup.md) 接入，保留已有模型选择、权限和工具限制，不擅自放宽平台限制。

### 4.3 Git Hooks

含 **HARNESS_PROJECT_CHECKS_PENDING** 的脚本只准备、不启用。按 [检查命令接入](setup-checks.md) 连接项目命令，验证正常与失败路径后启用；旧脚本的有效检查和准备步骤须保留。

## 5. 独立交付审阅

### 5.1 准备审阅

接入及调用核验后，使用**未参与本轮生成的 Reviewer 和独立上下文**审阅。可复用已核验角色，无需另建常驻角色。

主 Agent 提供源 Skill、原项目规则、用户确认的差异、最终产物和验证记录。Reviewer 直接读取文件及实际差异，只读审阅；缺证据则要求补验，不以完成摘要代替证据，也不默认重跑全部检查。

### 5.2 核对入口与流程

| 对象 | 核对内容 |
|---|---|
| **Index** | “何时读取、主题、文件”三列及真实路径齐全；只含跨任务入口，项目专属长期规则可定位，无具体任务链接或新增的当前任务登记入口 |
| **Workflow** | 对照 assets/agents.md 核对完整章节：阶段表、创建命令、恢复入口与用户批准条件；项目差异有批准依据，不用摘要替代流程 |
| **任务恢复** | 原任务文件未因清理索引被改写或删除；当前分支与 Overview Meta 能按 §2.5 定位任务，有歧义就报告，不按最新日期猜选 |

用不同阶段发现问题的场景，核对 **AGENTS.md §2.3.4** 的主 Agent 判断、派发和返工：返回位置、角色权限、受影响验证及独立复审均须连贯，不能只看标题或 05 Review 是否存在。

### 5.3 核对任务与记录

- **创建证据**：检查主 Agent 在隔离目录创建任务的产物，00–06 文件及 Plan §1–10 齐全；缺证据由主 Agent 补验。
- **Plan 正文**：直接阅读模板与副本，重点核对 §6.1–6.4、§9 实施就绪、§10 完成检查及跨文件引用；已填写的当前 Plan 同样检查，不只看文件存在。
- **记录职责**：对照原模板，确认无无关执行过程或重复记录；新增章节、职责变化须有用户确认，不只看标题齐全。

### 5.4 核对配置与执行证据

AGENTS、角色专题、原生配置和有效权限须一致；冲突由用户决定，不能擅自缩减职责后报完成。

角色专题只保留职责、派发规则、配置入口和简短接入摘要。摘要须注明适用范围，未经复验不刷新为通过；不堆积执行流水，根入口也不复制接入状态。

**执行证据需证明：**

- 项目内容和历史已保留；命令、Hook 和角色接入有实际依据，未知、失败及未执行均如实记录。
- Implement 在 Green 后完成必要的最小重构及复测；Review 核对执行证据，并按 code-review.md §1 独立理解，有疑点才比较。

明确规则不能降为可选，工具通过也不能代替语义审阅。

### 5.5 给出结论

返回 **通过／不通过、问题位置与依据、缺口及影响**。核心流程或必需 Plan 章节缺失，判为不通过。

主 Agent 在授权范围内批量修正或补验，再交 Reviewer 复核；需用户决定的冲突先报告。缺少独立审阅或仍有关键阻塞时，按 [完成与反馈](../SKILL.md#完成与反馈) 报告未完成。
